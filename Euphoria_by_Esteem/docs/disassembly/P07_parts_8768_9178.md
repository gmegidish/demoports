# P07: parts 0000:8768 (VESA torus, 497.40-527.50 s) and 0000:9178 (Rubik cube, 527.50-554.60 s)

## Summary

**Part 0000:8768, "torus over a cycling rainbow picture", VESA 640x480.**
- It loads the 640x480 picture `res/41.pcx` into both VESA video pages. The picture uses colour indices 1..199.
- Palette 1..200 is replaced by a 5-segment rainbow gradient. The picture is then animated by `rotatePalette(1,200,3)` once per frame.
- A procedural torus (20x10 quads, 0e5a:2117) is drawn with flat Lambert shading and per-scanline colour cycling, in colours 201..255 (dark blue to white).
- The torus is drawn straight into banked VESA memory through a VESA span routine (186a:1c8f).
- It is double-buffered with VESA display start (page 0 = scanline 0, page 1 = scanline 512).
- Only two 64 KB banks of the draw page (page rows ~102..307) are restored from a saved copy every frame.
- Timeline:
  - black for 3.2 s;
  - a 64-frame fade-in, during which the torus flies in from the right, wobbles, and flies out to the left;
  - 25 s of animation;
  - a palette fade-out to 30.00 s after the part start.
- It ends with setMode(0).

**Part 0000:9178, "Rubik's cube", mode 13h 320x200.**
- Background: picture `res/34.pcx` (the ESTEEM logo / statue), with its colours moved to 62..253.
- 27 cubies (0e5a:0929, boxes of 20 units with 6 coloured faces) are merged into one TGroup.
- The cube is scrambled invisibly with 15 random quarter turns (Random(9), so it is different on every run).
- Timeline:
  - fade in (1 s);
  - the cube swings in from below (orbiting the world origin) for 3 s;
  - it is solved on screen by replaying the 15 moves in reverse, one 90-degree turn per 0.9 s;
  - at t = 16.5 s it explodes: the cubies fly apart and toward the camera while the whole group drifts down;
  - at t = 23 s, a 0.5 s fade to white, then a fade to black until 27.00 s after the part start, then clearScreen.

**Checked against the capture** (capframe at 497.5..554.5, step 2.5 s, plus single frames):
- 8768: the first two sheet frames are black (3.2 s wait); the rainbow picture follows; a light-blue torus moves right to left.
- **I measured the frame rate of the reference:** I fitted the palette rotation offset (3 entries per frame) to the captured pixels against `res/41.pcx`. Every fit had zero error. The offset grows by 7 frames per 0.1 s (505.0 -> 505.1 -> 505.2: k = 120, 127, 134; 505.5: 154; 506.0: 189). So **the reference runs this loop at 70 frames/s**. The palette fade-in (64 frames) and the cycling speed depend on that rate.
- Many captured frames show the torus only partly drawn (for example 506.05 and 506.1). GUESS: an artefact of the capture emulator's handling of VESA display start / page flipping, not of the code: the code draws into the hidden page and flips afterwards. A faithful port should show complete frames.
- 9178: black at 527.5; the cube enters from the lower right (orbit) around 530; it is solved (one colour per face) at ~545; cubies explode at ~547.5; there are none at 550; whitish at 552.5; black at 555. All consistent with the reading below.

## 0000:819c copyBank(src: far ptr [bp+8], dst: far ptr [bp+4]) near, `ret 8`
`rep movsd` of 0x3fff dwords plus one `movsw`: copies **65534 bytes** (not 65536) from src to dst. The last 2 bytes of the 64 KB bank are never copied.

  - After t = 1900 it accelerates off to the left.

### How the 640x480 frame is composed (exact)
- VRAM is linear with 640 bytes per row. It is seen through the 64 KB window A at A000:0000, and bank n maps VRAM `n*65536 .. n*65536+65535`. The code assumes 64 KB granularity.
- **Page 0** = VRAM 0 (rows 0..479). **Page 1** = VRAM 5*65536 = 327680 = row 512 (rows 512..991). Rows 480..511 are never used.
- Display start: (0,0) shows page 0 and (0,512) shows page 1, through INT 10h 4F07h with BL = 0 (no retrace wait).
- **Initial content:** both pages hold `res/41.pcx` (indices 1..199), decoded by loadPCX (wide path, row 0 of the draw page). Everything else in VRAM is 0.
- **Per frame:**
  1. Restore the draw page's bank 1 and bank 2. In page-relative bytes that is 65536..131069 and 131072..196605: from (row 102, x 256) to (row 307, x 125). The bytes are taken from page 1's banks 6 and 7, saved once before the loop; they are identical to page 0's banks 1 and 2 because the picture is the same. The 2 bytes at page offsets 131070-131071 (row 204, x 510-511) and 196606-196607 (row 307, x 126-127) are never restored.
  2. Draw the torus polygons into the draw page.
  3. Flip.
  So the background outside rows ~102..307 is never touched. The torus must stay inside that band, otherwise it leaves trails. By the geometry (|vertex| <= 60, y in [-75, 5], D = 500) the screen y range is ~104..306, so it fits.
- **Port:** keep one VRAM array of 1024x640 bytes (or two 640x480 pages), with a draw-page base of 0 or 512 rows. Restore page rows from the saved copy using exactly the byte ranges above. Draw the torus with the FlatPoly rules (L2) into the draw page, and display the other page. Palette: 6-bit shadow with clamp, as in L1.

## 186a:1c74 / 186a:1c8f VESA solid span (spanFn), far, register args (not documented in L1)
In (spanFn convention): SI = x, DI = y, CX = len (>= 1), AL = colour. ES:BX is ignored (it uses DS:5d7a = A000:0000).
```
x2 = x + len - 1
// 1c74:
xx = x + clipLeft(DS:5bfa); yy = y + clipTop(DS:5bfc)          // NOTE: clip origin added as a viewport offset (0 here)
off32 = (uint16)W * (uint16)yy + (uint16)xx                  // 16x16 unsigned mul -> DX:AX, add x with carry
setBank(off32 >> 16)                                          // byte arg; absolute bank = that + DS:5d91 (the draw page)
di = off32 & 0xffff
// 1c8f:
n = x2 - x + 1
if (di + n <= 0xffff) fill(A000:di, n, AL)
else { first = 0x10000 - di; fill(A000:di, first, AL); nextBank(); fill(A000:0, n - first, AL) }
```
- **No clipping at all.** FlatPoly already clamps xl/xr to the clip rect, but its rows are not clipped to clipTop/Bottom, and this span does not check y. A negative y gives a huge unsigned offset (a write into some other bank).
- In this part y stays well inside, so a port can simply write `vram[pageBase + y*640 + x .. +n-1]`.
- The edge case di + n == 0x10000 also takes the split path (the second part is empty; the bank is advanced; harmless).

## 0e5a:2117 Torus.Init(R, r: Real48; nU, nV: int16; flags: word; minColor, maxColor: byte) constructor, far, `retf 0x1c`
Stack: R = Real48 [bp+0x1c..0x20], r = Real48 [bp+0x16..0x1a], nU = [bp+0x14], nV = [bp+0x12], flags = [bp+0x10], minColor = byte [bp+0x0e], maxColor = byte [bp+0x0c], VMT word [bp+0xa], self [bp+6].
Returns self in DX:AX (nil if the allocation failed).
Only caller: 8292 with (40.0, 20.0, 20, 10, 9, 201, 255), VMT DS:0cde. DS:0cde = {size 0x94, -0x94, 0, 0, 1342:2906 Done, 1342:29cf DoneFree}, i.e. a TPolyObject.
Constants: cs:2109 = PI (float80 3.141592653589793), cs:2113 = 180.0 (float32).
Locals: three Vec3 rings of 12-byte records, indexed 1..nV (index 0 unused):
- `cur[j]` at bp-0x264 + 12j
- `prev[j]` at bp-0x4bc + 12j
- `first[j]` at bp-0x714 + 12j

Also `havePrev` (byte [bp-0x731]).
```
TPolyObject.Init(limit = (uint16)(nU*nV), flags, minColor, maxColor)     // 287c, VMT arg 0
havePrev = 0
for (i = 1; i <= nU; i++) {
   a = Real48( (float)(int32)(int16)(i*360) / (float)nU )      // 16-bit imul, cwd, fild; extended divide
   for (j = 1; j <= nV; j++) {
      b  = Real48( (int32)(int16)(j*360) / (float)nV )
      rr = Real48( sin(b*PI/180.0) * r + R )                   // ext: Real48 b * PI(ext) / 180.0f, Sin, * r, + R
      x  = Real48( sin(a*PI/180.0) * rr )
      y  = Real48( cos(a*PI/180.0) * rr )
      z  = Real48( cos(b*PI/180.0) * r )
      MakeVec(f32(x), f32(y), f32(z), &cur[j])                 // Real48 -> extended -> fstp dword
   }
   if (havePrev) {
      for (j = 1; j <= nV-1; j++) AddQuad(prev[j], cur[j], cur[j+1], prev[j+1])
      AddQuad(prev[nV], cur[nV], cur[1], prev[1])
   } else {
      Move(&cur[1], &first[1], 600)                            // 0x258 bytes = 50 vectors
   }
   havePrev = 1
   Move(&cur[1], &prev[1], 600)
}
// close the ring: cur == prev == ring nU here
for (j = 1; j <= nV-1; j++) AddQuad(first[j+1], cur[j+1], cur[j], first[j])   // = (first[j+1], last[j+1], last[j], first[j])
AddQuad(cur[nV], first[nV], first[1], cur[1])
return self
```
- **Geometry:** ring i lies at angle a = 360*i/nU around the z axis: x = (R + r sin b) sin a, y = (R + r sin b) cos a, z = r cos b. Ring nU (a = 360) closes onto ring 1 (a = 18 degrees).
- **Faces:** (nU-1)*nV + nV = nU*nV = 200 quads. All have the same winding (the closing quads are cyclic rotations of the normal pattern).
- **Vertices:** AddQuad creates 4 new TPixels per quad, and AddFace deduplicates them by exact pos (the mesh flags have no 0x100). Copied rings hold bit-identical floats, so the mesh ends with nU*nV = 200 unique vertices, listed in first-appearance order.
- For nU = 20 and nV = 10 the angles are exact (18i and 36j degrees).
- **Colours:** face k gets colour (201 + k) & 255 (colour step 1; there is no SetColorStep call). This is irrelevant, because flags = 9 means shading mode 8 (flat Lambert, TFace.Shade overwrites the colour every frame: 201 + |54*dot/len|, clamped to 255) and fill type 1 (FlatPoly with cycLo = 201 and cycHi = 255, so the colour steps by +1 per scanline and bounces at 255).
- The faces are single-sided (no 0x40), so backface culling applies.
- Port: all values pass through Real48 (40-bit mantissa) and then f32. Doubles followed by Math.fround is enough (GUESS: identical).

- **Timing:**

  - Drop-in: t = 0..300.
  - Solve: each turn takes 90 ticks, so 15 turns take 1350 ticks (t = 300..1650).
  - Explosion: t from 1650 (e = t - 1650) to t = 2300.
  - Fades: then +0.5 s, then to 27.00 s.
  - main waits until tick 55460.
- **Frame-rate dependence:** the motion is purely time based. The only frame-dependent behaviour is the turn snapping. A turn is completed when the accumulated |angle| hits exactly 90. With >= 2 ticks per frame, `cur` can snap early, so the next turn starts a little late; the cumulative effect is small.
- **Pivot quirk:**
  - During the drop the pivot is reset to (0,0,0) after each MoveTo, so the cube orbits the origin while it rises (y = 300 - t, screen y down). Seen in the capture: it enters from the lower right.
  - On the first solve frame, MoveTo(0,0,0) moves the pivot by d = (0, t_last - 300, 0), where t_last is the last drop-phase t. So the pivot becomes (0, t_last - 300, 0), a few units at most, and it stays like that.
  - During the explosion, each group.MoveTo moves the pivot along with the group. Port TMesh.MoveTo literally and this comes out by itself.
- **Explosion composition:** a vertex ends at local + cubeTarget + groupOffset. cube.MoveTo moves by (target - cube.origin); the cube origin is not moved by group.MoveTo. The group offset therefore accumulates in the vertices and is replaced each frame by group.MoveTo's delta. With D = 200, the cubies vanish (faces culled when a vertex has z >= D) once z ≈ e^3/300000 + offset approaches 200 (e ≈ 380, t ≈ 2030).
- **Random:** the number of Random(9) calls varies (rejection loop), so RandSeed afterwards depends on the run.
- **Quirk:** for n = 1, `hist[0]` is the loop byte itself (= 1), so the first move can never be 1, 2 or 3.
- **DS:9118 (gradStep):** set to -80 by 8dfa and to 0 in the explosion. No face here uses it (the cubie faces are fill type 1, not 2). It persists into the next part.
